01 / Start here

Open your working demo

On this computer, open http://localhost:3200. The app was started locally; if it has stopped, open PowerShell in the project folder and run:

npm run dev

Leave that terminal running. Press Ctrl+C there to stop the app. The database can remain running. Ports 3000 and 3100 belong to other applications; this project uses 3200.

02 / Daily worker workflow

Take a record through the care loop

Sign in with the worker account. On a phone, use the navigation menu to reach all sections. This walkthrough uses invented adult details only.

1. Register a fictional adult

Use the enrolment action and complete the three-step registration form. Enter the fictional person's details, review the consent step, choose optional SMS/WhatsApp permissions, and submit. Confirm the record appears in Mothers. Essential enrolment consent and optional reminder consent are separate.

2. Schedule an appointment

Open the mother's record, enter the visit date and appointment details, then save. Scheduling creates a follow-up task automatically. Use Appointments to review planned visits.

3. Record the contact outcome

Open Follow-ups or the record's follow-up controls. Record reached, no answer, rescheduled or declined. For no answer and rescheduled, supply the next action date. Save and verify the updated task status.

4. Track a referral to closure

Create a referral from the mother's record. Use the permitted status actions to record acceptance and attendance, then close it with a coordination note. Each transition is validated and audited; closure should represent a confirmed coordination outcome in the demo.

5. Check the result

Review the record timeline and Impact. Sign out while connected, then sign in as the clinic coordinator. The clinic's closure metrics include the worker's completed referral. Small aggregate cells are suppressed to limit disclosure.

What “done” means in the demo
The record was saved, an appointment created its follow-up, the outcome was recorded, the referral completed its allowed transitions, and clinic metrics reflect closure.

Consent changes and archiving

Use the record's consent and archive actions when available to your role. Withdrawing reminder permission should prevent further simulation on that channel. Review confirmation text before archiving. Archiving is not an approved legal erasure process.

Workers see assigned records. A missing record may reflect assignment or clinic scope; ask the coordinator to check access rather than copying records into another account.

03 / Roles, messages and security

Explore the rest of the system

Role / section Available use
Clinic coordinator Coordinate care inside the clinic, review clinic impact and manage the clinic team/assignments through the available controls.
Programme admin Manage facilities and access; view suppressed programme aggregates. Patient lists and care timelines are unavailable.
Auditor Review audit metadata and suppressed aggregates. No contact details or patient record browsing.
Message library Review approved source templates and deterministic drafts. A new draft requires review; it is not automatically approved or sent.
Audit trail Inspect permitted action metadata. Logs avoid contact details, message bodies and clinical notes.

Simulate a reminder

  1. Open an assigned record with the relevant reminder consent.
  2. Choose the available neutral template/channel and preview the message.
  3. Use the simulation action and inspect its recorded result.
  4. Withdraw that channel's consent and verify a further simulation is rejected.
There is no live SMS or WhatsApp connection. No reminder reaches a phone. The content assistant uses approved local sources and deterministic drafting; it does not call an external AI service or accept patient prompts.

Enable your two-factor sign-in

Use a dedicated test account so shared demo logins remain available. Open the account security controls, confirm your current password and start authenticator setup. Add the displayed secret to an authenticator app, enter its current code and complete activation. Subsequent sign-in needs password plus code. Codes cannot be reused after acceptance. Keep the authenticator available; self-service MFA recovery is not provided.

Enabling MFA revokes older sessions. Password resets and deactivation also invalidate stale sessions, including sign-ins racing with the change. Local recovery is a localhost development simulator; hosted verified recovery is still required.

Sign out safely

Reconnect before signing out. Successful sign-out revokes the server session and wipes the tab's queued offline changes, encryption key and in-memory records. If offline, the app asks you to reconnect so revocation can complete.

04 / Offline use

Capture offline, then synchronize

Offline support is designed around a prepared tab and an encrypted pending registration queue. It does not provide a complete offline database of all mothers.

  1. Prepare while connected. Sign in and open /offline at the same localhost origin. Let the offline shell and static assets load.
  2. Keep the same tab. Disable connectivity using browser developer tools to simulate offline mode. For this localhost demo, disabling Wi-Fi alone may leave the local server reachable.
  3. Test refresh. Refresh offline after preparation. The public registration shell should load.
  4. Register a fictional adult. Complete the form and submit. Verify it is queued locally; it is not yet a server record.
  5. Reconnect. Use Sync now in the offline shell or the Offline queue section.
  6. Confirm the result. Check that the queue clears and the new record appears in Mothers. Schedule its appointment after synchronization.

Limits you need to know

  • Pending payloads are encrypted in IndexedDB. Their key stays in tab-session storage, and queued changes expire after 24 hours.
  • Closing the tab, clearing browser storage or signing out can lose queued work or its key. Synchronize before doing those actions.
  • Already-loaded records can remain in memory during a connection loss. Offline refresh supports registration; it does not restore previously loaded patient detail.
  • Only public shell/static assets are cached. Personalized HTML and API responses are not stored in the service worker's cache.
  • Synchronization rechecks authentication, consent, clinic/assignment scope and record version. Duplicate replay is handled idempotently.

If synchronization fails

Reconnect and confirm you are using the same account/tab. Read the error. If assignment, consent or version changed, refresh the authoritative record and reconcile with the coordinator. Discard obsolete queued content and re-enter the correct action where appropriate. Do not force an overwrite.

Before leaving a workstation
Connect → synchronize → verify records → sign out. A tab-held key is an additional control, not a substitute for device security or an approved lost-device process.

06 / Completion plan — engineering

What remains, and how to finish it

1. Finish reproducible hosted-demo deployment

Owner: developer / deployment lead. Resolve Docker's registry connectivity or proxy issue and repeat docker build -t nurturepath-demo:reviewed .. Keep TLS verification enabled. Run the built image against a separate synthetic database, then verify health, sign-in and referral closure. Alternatively validate a managed Next.js deployment using docs/deployment.md.

Acceptance: immutable build, passing container/hosted smoke tests, TLS/exact origin, secure cookies, controlled migrations, unique secrets and tested rollback. No hosting account or public domain is currently provisioned.

2. Connect identity, keys and audit infrastructure

Owner: developer + security lead. Add verified recovery delivery and single-use recovery tests. Connect a managed key service to the versioned encryption keyring; exercise rotation and restored-backup decryption. Export redacted audit metadata to an access-controlled immutable store.

Acceptance: reviewed recovery abuse controls, access/key-rotation drills and tamper-evidence assessment. Do not replace the sole decryption key in place.

3. Build the live reminder pipeline

Owner: developer + partner/content owners. After approved provider arrangements, implement durable scheduled jobs, retry/backoff, deduplication, quiet hours, opt-out/STOP processing and authenticated delivery webhooks. Recheck consent immediately before every send; avoid clinical details in neutral copy.

Acceptance: provider-sandbox tests demonstrate consent withdrawal, retry safety, signed-webhook rejection, duplicate handling and opt-out. Keep the simulator active until release approval.

4. Close performance, accessibility and content gaps

Owner: developer + independent reviewers. Profile scoped reads and database plans, improve measured bottlenecks, and repeat a documented staging load test. Complete keyboard/screen-reader, mobile OS and device-storage assessment. Extend content governance with reviewer identity, source/version, approval history and qualified translation review.

Acceptance: p95 under 800 ms at an agreed load, resolved accessibility findings and versioned content approval. No current local-language publication or validated clinical translation is claimed.

Recommended order
Working hosted synthetic demo → identity/key/audit infrastructure → provider sandbox and content governance → independent tests and exercises → written gates → monitored pilot.

Then release a limited pilot

  1. Review all six approvals and remaining findings together.
  2. Approve hosting/database/provider contracts and separate environments.
  3. Test backup, migration, rollback, monitoring and the same immutable release artifact.

Changing DEMO_MODE is not approval. In this release, DEMO_MODE=false blocks care writes. Do not bypass that control to enter real records. Real-data launch requires a subsequent reviewed software release.

08 / Maintain and hand over

Keep the demo working

Routine checks

npm run lint
npm run typecheck
npm test
npm audit --omit=dev

Database tests need the migrated/seeded local database. For a release check, stop the server first on Windows, then build and start: 

npm run build
npm run start
# In a second PowerShell terminal:
$env:PLAYWRIGHT_CHANNEL='chrome'
$env:PLAYWRIGHT_PRODUCTION='true'
npm run test:e2e

Browser tests leave clearly labelled fictional E2E records. The guarded reset command is documented in README.md; it clears local demonstration care records, so review its confirmation requirements first.

Common problems

Symptom Action
